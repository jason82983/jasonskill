# 4-1 打样评审检查框架

本文件补充 `SKILL.md`，只用于真实样品评审，不替代 3-3 方案评审或 4-2 量产前检查。

## 放行前提

| 3-3 最新状态 | 4-1处理 |
|---|---|
| 【通过｜进入打样】 | 正常执行 |
| 【有条件通过｜完成指定事项后进入打样】 | 先逐项核对条件完成证据；未完成则输出 `[3-3打样前条件尚未完成]`，不得假装放行 |
| 【退回3-2修改】/【停止该方案】/【证据不足，暂不决策】 | 原则上不执行正式 4-1 |

## 样品身份与证据清单

首先锁定：样品编号、打样轮次、对应 3-3 版本、对应 3-2 方案、打样日期、工厂/供应商（如有）和资料来源。存在 Sample V1/V2/V3 时不得混用。清单逐项记录文件名、样品、日期、证据类型和本次用途。

允许的证据标签：

`[图片可见]`、`[视频可见]`、`[实测数据]`、`[测试结果]`、`[工厂确认]`、`[供应商确认]`、`[人工体验]`、`[文件记录]`、`[AI推断]`、`[待验证]`。

观察只能支持观察结论。例如照片看到划痕只能写 `[图片可见]`；不能由照片推断承重、材料牌号或舒适度。没有人工体验记录时，手感、舒适、安装和主观外观必须写 `[人工体验待验证]`。

## 批准方案—真实样品一致性矩阵

至少比较产品定义、P0/P1、核心结构、材料、关键尺寸/规格、功能、配件、BOM V1、工艺、CMF、使用/安装方式、包装、打样必须实现项和禁止偏离项。每行只使用：`【符合】`、`【部分符合】`、`【不符合】`、`【无法验证】`。不得用综合评分替代判断。

偏差不自动等于失败；判断偏差是否影响 P0/P1、核心消费者价值、功能、购买理由、安全或工程逻辑。局部非核心偏差可以进入修改清单，核心偏差必须决定重打、退回或暂不决策。

## 核心功能与工程验证

按链条记录：P0/P1 → 设计目标 → 3-3批准要求 → 样品实际状态 → 证据 → 验证方法 → 结果 → 问题 → 下一步。没有真实测试不得写“验证通过”，只能写 `[待验证]`。

## 消费者实际体验验证

只评与当前产品有关的使用便利性、安装便利性、操作复杂度、手感、稳定性、舒适度、消费者感知、购买理由和新增负面体验。AI 不得代替真人体验；有记录时保留原意并标记 `[人工体验]`。

## 外观、工艺与初步质量

检查 CMF、表面处理、做工、接缝、毛刺、装配、对齐、结构稳定、配件匹配、明显缺陷、外观一致性和包装样品。这是样品阶段初步评审，不是最终量产 QC。

## 问题归因与回退

每个问题至少记录问题、证据、影响、严重程度和处理方式。归因只允许：

`【设计问题】`、`【工程实现问题】`、`【供应商执行问题】`、`【材料问题】`、`【工艺问题】`、`【规格偏差】`、`【体验问题】`、`【包装问题】`、`【信息不足】`、`【归因待确认】`。

- 设计逻辑错误 → 退回 3-2；不得由 4-1 重新设计完整方案。
- 方案逻辑正确但工厂未按要求执行 → 工厂整改或重打。
- 局部工程、材料、工艺、规格或体验问题 → 修改后重打。
- 信息不足 → 补证据后重评。
- 同一核心问题连续多轮无法解决 → 标记 `【建议重新评估产品方案】`，不得无限机械重打。

## 最终状态

只允许：

1. `【通过｜进入4-2量产前检查】`
2. `【有条件通过｜完成指定修正后进入4-2】`
3. `【修改后重打】`
4. `【退回3-2重新开发】`
5. `【证据不足｜暂无法完成样品评审】`

通过不等于批准量产。有条件通过必须写明修正内容、完成证据和为何无需重新完整 4-1；必要重打不得被有条件通过绕过。

## 4-2 交接包门槛

只有前两种状态且条件已经满足，才生成正式《4-2输入交接包》。至少包含通过样品身份/轮次、3-3/3-2来源、核心定义、P0/P1、已验证消费者价值与功能、结构、材料、规格、功能组合、配件、BOM、工艺、CMF、包装、【样品阶段已验证】、【量产前必须确认】、【不得未经重新评审修改】以及成本、供应链、质量、IP、合规和量产风险。
