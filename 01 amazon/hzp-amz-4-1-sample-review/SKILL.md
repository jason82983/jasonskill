# HZP Amazon 4-1｜打样评审

## 定位与边界

4-1 是“3-3 纸面方案评审 → 4-2 量产前检查”之间的真实样品评审。它回答：真实样品是否做出了批准的产品方案；如果没有，问题在哪里、应由谁解决、下一步是通过、修正重打还是退回开发。

- 3-2 = 产品方案开发；3-3 = 纸面方案评审/打样放行；4-1 = 真实样品评审；4-2 = 量产前检查。
- 只评真实样品和样品证据，不重新做 2-1/2-2/2-3/3-1/3-2/3-3，不重新完整设计产品，不批准量产，不替代最终 QC。
- 一次运行连续完成所有已定义检查，不要求用户逐阶段确认；样品身份、3-3 放行或关键证据无法安全确认时停止。

## 产品身份与上游输入

1. 在当前已锁定 Product Root 读取 `01_产品档案.md`，取得产品编号和产品中文名称。缺失、冲突或无法确认时停止，输出 `[产品档案缺失]`、`[产品身份冲突]` 或 `[产品身份无法确认]`；禁止根据 ASIN、目录名或报告名猜测。
2. 只在同一 Product Root 的 `06_SKILL分析报告/` 递归查找当前产品最新有效的 3-3 正式 HTML。优先读取《4-1输入交接包》，并先检查 3-3 是否真正允许进入打样。
3. 若 3-3 为 `【有条件通过｜完成指定事项后进入打样】`，必须逐项找到条件完成证据；未完成或无法确认时输出 `[3-3打样前条件尚未完成]`，不得假装进入正式 4-1。
4. 若 3-3 为 `【退回3-2修改】`、`【停止该方案】` 或 `【证据不足，暂不决策】`，原则上不得执行正式 4-1，说明阻断原因和重新运行条件。

## 上游正式报告最新版与追溯规则

所有上游 Skill 正式报告只能从当前 Product Root 的 `06_SKILL分析报告/` 查找，不得跨 Product Root。候选文件必须同时匹配当前产品编号和目标 Skill 编号，并优先符合：

`[Skill编号]_[产品编号]_[技能中文名称]_V[版本号]_[YYYYMMDD]_[HHMMSS].html`

解析 Skill 编号、产品编号、V 版本号和文件名时间戳；先取最大 V，同 V 再取文件名时间戳最大者。不得依赖目录顺序、文件系统返回顺序、modified time、created time 或找到的第一个文件。`index.html`、Draft、Preview、Test、Temp、Demo、Debug、失败、未完成、废弃、无效和临时输出不是正式输入；无版本号或无文件名时间戳的旧文件只能作为历史参考。

如果最新候选有效性无法可靠确认，输出 `[上游报告有效性无法确认]`，列出目标 Skill、候选文件名和原因，不得偷偷退回旧版。若最新版疑似错误或数据异常，仍以最新版为当前输入并标记 `[建议复核上游最新版]`。默认只使用各目标 Skill 最新有效版本，不与旧版拼接或混用；只有明确调查版本变化时读取旧版，并标记 `[历史版本对照]`。

凡本次实际读取上游正式报告，正式 HTML 必须包含《输入版本追溯》，记录上游 Skill 编号、中文名称、实际文件名、版本号、文件名生成时间、输入类型（`【核心输入】`、`【辅助回查】`、`【历史版本对照】`）和用途。未实际读取的报告不得写入。`01_产品档案.md` 和 `07_产品资料/` 等非版本化资料继续按原规则读取。

## 真实样品证据门槛

4-1 必须主动检查当前 Product Root 的 `07_产品资料/`，寻找与本次真实样品直接相关的照片、视频、样品编号、打样轮次、实测尺寸/重量、材料确认、结构/BOM、工厂说明、供应商确认、报价、测试数据、包装样品、人工体验、问题记录和修改记录。

如果完全没有真实样品，或没有任何能够代表样品状态的可靠证据，输出 `【证据不足｜暂无法完成样品评审】`，列明缺什么、为什么重要、如何补充。不得只凭 3-2/3-3 纸面方案假装样品通过。

严格使用证据标签：

`[图片可见]`、`[视频可见]`、`[实测数据]`、`[测试结果]`、`[工厂确认]`、`[供应商确认]`、`[人工体验]`、`[文件记录]`、`[AI推断]`、`[待验证]`。

照片可见的划痕只能写 `[图片可见]`，不得据此推断承重、材料牌号或安全测试结果；没有人工体验记录时，手感、舒适、安装、操作或主观外观感受必须写 `[人工体验待验证]`；图片像某种材料不等于材料已确认。

## 固定执行流程

读取身份 → 读取最新有效 3-3 → 检查 3-3 放行条件 → 优先读取《4-1输入交接包》 → 锁定样品编号/轮次 → 读取真实样品证据 → 按需回查最新 3-2/3-1/2-3/2-2/2-1 → 样品身份与证据清单 → 批准方案—真实样品一致性 → 核心功能与工程验证 → 消费者实际体验 → 外观/工艺/初步质量 → 问题识别与归因 → 反方检查 → 决定通过/有条件通过/重打/退回/暂不决策 → 按需生成修改清单或 4-2 交接包 → 生成正式 HTML → 确认落盘 → 调用 0-2。

## 1. 《样品身份与证据清单》

首先确认样品编号、打样轮次、对应 3-3 版本、对应 3-2 方案、打样日期、工厂/供应商（如有）、证据来源和完整性。Sample V1/V2/V3 必须分开，不能混用。清单列出本次实际使用的照片、视频、实测、测试、工厂反馈、人工体验、报价、BOM、结构资料和其他证据，并标注证据类型、样品、日期和用途。

## 2. 《批准方案—真实样品一致性矩阵》

至少比较：产品定义、P0/P1、核心结构、材料、关键尺寸/规格、功能、配件、BOM V1、工艺、CMF、使用/安装方式、包装、打样必须实现项和禁止偏离项。每项状态只允许 `【符合】`、`【部分符合】`、`【不符合】`、`【无法验证】`，禁止 87/100、92 分或综合一致性评分。

偏差不自动等于失败；必须判断偏差是否影响 P0/P1、核心消费者价值、核心功能、购买理由、安全或工程逻辑。轻微非核心偏差可进入修改清单，核心偏差必须重点处理。

## 3. 《核心功能与工程验证》

按证据链记录：P0/P1 → 设计目标 → 3-3 批准要求 → 样品实际状态 → 证据 → 验证方法 → 验证结果 → 问题 → 下一步。没有真实测试时只能标记 `[待验证]`，不得写验证通过。只验证当前产品真正相关的工程和功能项目。

## 4. 《消费者实际体验验证》

评审与当前产品有关的使用便利性、安装便利性、操作复杂度、手感、稳定性、舒适度、消费者感知、实际购买理由和新增负面体验。真实人工反馈标记 `[人工体验]` 并保留原意；没有记录则标记 `[人工体验待验证]`，不得由 AI 补全。

重新回验 3-2/3-3 认为消费者会感知的差异，例如稳定、易开箱、低复杂度是否在样品阶段真实出现。没有真实证据，不能判定消费者价值已验证。

## 5. 《外观/工艺/初步质量评审》

按产品实际情况检查 CMF、表面处理、做工、接缝、毛刺、装配、对齐、结构稳定、配件匹配、明显缺陷、外观一致性和包装样品。这是样品阶段的初步质量评审，不是最终量产 QC。

## 6. 《样品问题归因表》

每个重要问题至少记录问题、证据、影响、严重程度和建议处理方式。归因只允许：

`【设计问题】`、`【工程实现问题】`、`【供应商执行问题】`、`【材料问题】`、`【工艺问题】`、`【规格偏差】`、`【体验问题】`、`【包装问题】`、`【信息不足】`、`【归因待确认】`。

- 设计逻辑本身错误 → 退回 3-2；4-1 不重新设计完整产品。
- 方案正确但工厂未按要求执行 → 工厂整改或重打。
- 局部工程、材料、工艺、规格或体验问题 → 修改后重打。
- 信息不足 → 补证据后重新评审。
- 同一核心问题连续多轮无法解决 → 标记 `【建议重新评估产品方案】`，不得无限机械重打。

允许提出局部尺寸纠正、工艺改善、装配调整、材料执行纠正和 CMF 调整；若必须改变核心产品定义、P0 解决逻辑、核心差异化、核心结构或使用方式，必须退回 3-2/3-3，不能由 4-1 越权完成。

## 7. 《反方检查》

正式结论前回答：样品最大成功点、最大失败点、是否把“看起来不错”当成验证通过、是否把 AI 推断当实测、是否把供应商说法当测试结果、是否因局部瑕疵误判整件方案失败、是否忽略工厂执行失败、问题属于设计还是执行、若进入 4-2 的最大风险，以及为什么作出当前结论。

## 最终评审状态

只允许以下五种状态：

1. `【通过｜进入4-2量产前检查】`
2. `【有条件通过｜完成指定修正后进入4-2】`
3. `【修改后重打】`
4. `【退回3-2重新开发】`
5. `【证据不足｜暂无法完成样品评审】`

通过不等于批准量产。有条件通过只适用于核心样品已经成立、剩余是明确低风险修正且不需要重新完整打样；必须写明修正内容、完成证据和为何无需重新完整 4-1。需要真实修改并重新验证时使用【修改后重打】。真实样品证明核心方案本身失败时才【退回3-2重新开发】，并生成《退回3-2原因》。

## 《下一轮打样修改清单》

当状态为【修改后重打】，逐项写明问题、证据、归因、影响 P0/P1、修改要求和目的、允许调整范围、不可破坏的核心设计、下一轮验证方法及成功判定条件。

## 《4-2输入交接包》

只有状态为【通过｜进入4-2量产前检查】或【有条件通过｜完成指定修正后进入4-2】且条件已满足时，才生成正式交接包。交接包必须包含通过样品身份/轮次、3-3/3-2 来源、核心产品定义、P0/P1、已验证消费者价值和功能、确认的结构/材料/规格/功能/配件/BOM/工艺/CMF/包装，以及：

- 【样品阶段已验证】
- 【量产前必须确认】
- 【不得未经重新评审修改】
- 成本、供应链、最终 BOM、最终规格、质量标准、包装运输、IP、合规和量产风险

其他状态不得假装已经进入 4-2。

## 正式 HTML 报告

保存到 `[Product Root]/06_SKILL分析报告/`，只新增不覆盖历史文件：

`4-1_[产品编号]_打样评审_V[最大版本号+1]_[YYYYMMDD]_[HHMMSS].html`

固定结构：产品身份与《样品评审结论》、输入版本追溯、样品身份与证据清单、批准方案—真实样品一致性矩阵、核心功能与工程验证、消费者实际体验验证、外观/工艺/初步质量评审、样品问题归因表、反方检查、按需显示的下一轮修改清单/退回原因、仅符合条件时的 4-2 输入交接包、数据与证据局限、名词术语解释。首页优先显示产品编号+名称、样品编号/轮次、3-3 版本、一句话结论、最终状态、P0/P1 实现、核心消费者价值和功能验证、最大样品问题、归因、最大待验证项和下一步动作。

报告以中文为主，使用样品证据卡、照片/视频说明、一致性矩阵、验证结果表、问题归因表、修改清单和放行结论卡。图表负责理解、表格负责查数、文字负责解释；禁止雷达评分、综合评分、AI 信心分、3D 图表和花哨动画。

## 0-2 联动与职责边界

正式 HTML 成功写入、确认文件存在且文件名正确后，调用 `hzp-amz-0-2-report-index`，原样传递本次已确认的 Product Code、Products Root、Product Root。4-1 不得扫描、创建、维护、排序或备用更新 `index.html`。报告失败时不调用 0-2；报告成功但 0-2 失败时保留报告，并明确返回“正式报告：生成成功；报告索引：更新失败；原因：[实际原因]”。

## 绝对禁止

禁止没有真实样品证据就完成正式评审；禁止 AI 视觉观察冒充测试、AI 推断冒充人工体验、图片判断冒充材料确认、供应商描述冒充测试结果；禁止重新完整执行前序 Skills、重新设计产品、把局部问题自动升级为方案失败、把方案问题简单推给工厂、无限机械重打、把未知写成失败、把待验证写成已通过、编造成本/工程/IP/合规/供应链事实、直接批准量产、修改历史报告/人工资料/原始样品证据或自行维护 `index.html`。

详细字段见 [references/sample-review-framework.md](references/sample-review-framework.md) 和 [references/handoff-schema.md](references/handoff-schema.md)；报告结构见 [templates/report-outline.md](templates/report-outline.md)。
