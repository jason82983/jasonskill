# HZP Amazon 3-3｜产品方案评审

## 定位与边界

3-3 是“差异化产品方案 → 真实打样”之间的正式评审关口。它回答：当前 3-2 推荐方案是否已经合理到值得投入时间和成本进入打样。

- 3-1 = WHAT + WHY；3-2 = HOW；3-3 = REVIEW / GATE；4-1 = SAMPLE VALIDATION。
- 只评审方案，不重新做 2-1/2-2 市场分析，不重新定义 3-1 机会，不替代 3-2 完整设计，不进行真实样品评审，不批准量产。
- 一次运行连续完成所有已定义检查，不要求用户逐阶段确认。只有产品身份、评审对象或关键输入无法安全确认时才停止。

## 产品身份与输入

1. 在当前已锁定的 Product Root 读取 `01_产品档案.md`，取得产品编号和产品中文名称。文件缺失、身份冲突或无法确认时停止，输出 `[产品档案缺失]`、`[产品身份冲突]` 或 `[产品身份无法确认]`；禁止根据 ASIN、目录名或报告名猜测。
2. 只在同一 Product Root 的 `06_SKILL分析报告/` 递归查找当前产品的最新有效 3-2 正式 HTML。优先读取其中的《3-3输入交接包》，并确认推荐方案 V1、推荐理由、P0/P1 对应关系、结构、材料、规格、功能、配件、BOM V1、工艺、CMF、包装、消费者价值、购买理由、Amazon 可表达差异点、约束和待验证项。
3. 按需回查当前产品最新有效的 3-1、2-3、2-2、2-1 正式报告，只为核实具体评审问题、机会依据、消费者证据或冲突；不得重新完整执行前序 Skill。
4. 按需读取当前 Product Root 的 `07_产品资料/`，仅作为结构、尺寸、工程、材料、工厂/供应商、报价、工艺、包装、测试或样品可行性证据。缺少资料时标记相应待验证状态，不得假装确认。

## 上游正式报告选择与输入版本追溯

所有上游 Skill 正式报告只能从当前 Product Root 的 `06_SKILL分析报告/` 查找，不得跨 Product Root。候选文件必须同时匹配当前产品编号和目标 Skill 编号，并优先符合：

`[Skill编号]_[产品编号]_[技能中文名称]_V[版本号]_[YYYYMMDD]_[HHMMSS].html`

解析 Skill 编号、产品编号、V 版本号和文件名时间戳；先选最大 V，同 V 再选文件名时间戳最大者。不得依赖目录顺序、文件系统返回顺序、modified time、created time 或找到的第一个文件。`index.html`、Draft、Preview、Test、Temp、Demo、Debug、失败、未完成、废弃、无效和临时输出都不是正式输入；无版本号或无文件名时间戳的旧文件只能作历史参考。

如果候选有效性无法可靠确认，必须输出 `[上游报告有效性无法确认]`，列出目标 Skill、候选文件名和原因，不得偷偷退回旧版。若最新版疑似错误或数据异常，仍以最新版为当前输入并标记 `[建议复核上游最新版]`。当前正式结论默认只使用各目标 Skill 的最新有效版本，不与旧版拼接、平均或混合；只有明确调查版本变化时才读取旧版，并标记 `[历史版本对照]`。

凡本次实际读取上游正式报告，正式 HTML 必须包含《输入版本追溯》，逐条记录：上游 Skill 编号、中文名称、实际文件名、版本号、文件名生成时间、输入类型（`【核心输入】`、`【辅助回查】`、`【历史版本对照】`）和本次用途。未实际读取的报告不得写入。`01_产品档案.md` 与 `07_产品资料/` 等非版本化资料继续按原规则读取。

## 固定评审流程

读取身份 → 读取最新有效 3-2 → 优先读取《3-3输入交接包》 → 按需回查 3-1/2-3/2-2/2-1 → 按需读取 07_产品资料 → 方案身份与完整性 → 机会—方案一致性 → 消费者价值与购买理由 → 差异化真实性 → 工程/成本/供应链可行性 → 风险分级 → 反方检查 → 方案放行决策 → 仅在允许状态下生成《4-1输入交接包》 → 生成正式 HTML → 确认落盘 → 调用 0-2。

### 1. 方案身份与完整性

明确正在评审的 3-2 版本、推荐方案、备选方案和核心产品定义。检查产品身份、P0/P1、结构、材料、规格、功能、配件、BOM V1、工艺、CMF、包装、成本、工程、供应链、IP、合规和关键验证项。缺失不自动等于失败；判断其是否影响“能否合理进入打样”。评审对象无法可靠确认时停止。

### 2. 机会—方案一致性

生成《机会—方案一致性检查》，逐项连接：3-1 P0/P1 → 3-2 设计目标 → 当前设计 → 消费者感知 → 购买理由。若方案偏离核心 P0，明确标记 `[P0解决不足]`，不得因外观高级或参数增加就判定通过。

### 3. 消费者价值与购买理由

评审消费者能否明显感知、理解和体验改进，是否形成真实购买理由、支持价格差异、降低负面体验、避免新问题，以及 Amazon 页面是否容易表达。工程升级不自动等于消费者价值。

### 4. 差异化真实性

生成《差异化真实性检查》。按需核对每个差异点对应的 P0/P1、市场现有配置、是否只是常规配置、是否明显更好、消费者可感知性、购买理由和 Amazon 表达能力。不得重新完整执行 2-2；市场普遍已有且没有明显改善的功能不得继续称为核心差异化。

### 5. 工程、成本与供应链可行性

评审是否存在合理工程路径、结构逻辑、材料方向、关键规格、连接/安装/使用逻辑、安全风险和验证方法。检查真实报价来源、成本目标、成本敏感设计、工厂和工艺路径、材料与特殊部件供应、制造障碍及单点风险。未知分别标记 `[工程待验证]`、`[成本待验证]`、`[供应链待验证]`，不得编造成本、报价、能力、良率、交期或测试结果。

### 6. 风险分级与反方检查

生成《风险分级与验证要求》，将风险分为：

- A｜打样前必须解决：核心结构无法打样、已确认重大安全/IP/合规问题、已确认完全不可接受的成本或核心定义冲突等；必须有可靠证据。
- B｜允许进入打样验证：厚度、手感、稳定性、安装体验、外观、配件、CMF 等可通过样品解决的问题。
- C｜后续量产前验证：最终量产 BOM、公差、良率、大货一致性、包装运输、最终价格和长期稳定性等。

严格区分未知与已确认风险：`[IP风险待验证]` 不等于侵权，`[成本待验证]` 不等于成本过高，`[供应链待验证]` 不等于无法生产。正式放行前执行《反方检查》：最强支持理由、最强反对理由、最大未验证假设、是否把工程升级当消费者价值、是否把常规配置当差异化、是否把未知当不可行、是否把待验证当已解决、最可能浪费打样成本的原因，以及为何仍作当前决策。

## 方案放行决策

最终状态只允许：

1. `【通过｜进入打样】`
2. `【有条件通过｜完成指定事项后进入打样】`
3. `【退回3-2修改】`
4. `【停止该方案】`
5. `【证据不足，暂不决策】`

不得使用 2-2 的 `GO / CONDITIONAL GO / NO-GO`。存在待验证项不自动拒绝；只要未知问题可以通过打样、测试、供应商确认或工程验证解决，就不自动阻止进入 4-1。只有有可靠证据的致命结构、安全、IP、合规、成本或实现路径问题才可【停止该方案】。

若【退回3-2修改】，必须生成《退回3-2修改要求》，说明问题、原因、对应 P0/P1、必须解决内容、不能丢失的价值及需要重新设计的范围；3-3 不得自行完成新方案。若【证据不足，暂不决策】，必须列明缺少的关键证据、获取方式和重跑条件。

## 《4-1输入交接包》

只有【通过｜进入打样】或【有条件通过｜完成指定事项后进入打样】才允许生成正式《4-1输入交接包》。它必须传递评审结论、批准的 3-2 方案及版本、核心产品定义、P0/P1、消费者价值、购买理由、结构、材料、规格、功能、配件、BOM V1 状态、工艺、CMF、包装和风险，并明确：

- 【打样必须实现】
- 【打样建议实现】
- 【禁止偏离】
- 样品成功判定条件和失败判定条件
- 样品阶段允许调整范围
- 不得未经重新评审修改的核心内容及回退 3-2/3-3 机制
- 工程、结构、材料、功能、使用体验、消费者感知、CMF、成本、供应链、IP、合规等待验证事项

成功/失败条件必须来自 3-1 机会、3-2 设计目标和本次评审；无法量化时可使用明确的定性标准，并标记 `[打样待验证]`。该交接包不是最终工程批准或量产批准。

## 正式 HTML 报告

保存到 `[Product Root]/06_SKILL分析报告/`，只新增不覆盖历史文件：

`3-3_[产品编号]_产品方案评审_V[最大版本号+1]_[YYYYMMDD]_[HHMMSS].html`

固定结构：产品身份与评审结论、输入版本追溯、方案身份与完整性检查、机会—方案一致性检查、消费者价值与购买理由评审、差异化真实性检查、工程可行性评审、成本与供应链评审、风险分级与验证要求、反方检查、方案放行决策、按需显示的退回要求、仅在允许状态下的《4-1输入交接包》、数据与证据局限、名词术语解释。首页第一屏优先显示产品编号+名称、3-2 版本/方案、一句话结论、放行状态、P0 解决情况、消费者价值、购买理由、差异化判断、最大风险、最大打样验证项和下一步动作；不要塞满工程参数。

报告以中文为主，图表仅在有实际数据意义时使用。优先评审卡片、机会一致性矩阵、差异化真实性表、工程/成本/供应链状态表、风险分级表和放行决策卡。禁止雷达评分、综合分、AI 信心分、3D 图表和花哨动画。

## 0-2 联动与职责边界

正式 HTML 成功写入、确认文件存在且文件名正确后，调用 `hzp-amz-0-2-report-index`，原样传递本次已确认的 Product Code、Products Root、Product Root。3-3 不得扫描、创建、维护、排序或备用更新 `index.html`。报告失败时不调用 0-2；报告成功但 0-2 失败时保留报告，并明确返回“正式报告：生成成功；报告索引：更新失败；原因：[实际原因]”。

## 绝对禁止

禁止重新做 2-1/2-2、重新定义 3-1 机会、替代 3-2 重新设计完整方案、未经证据增加核心方案、把工程升级等同消费者价值、把常规配置冒充差异化、把未知等同不可行、编造成本/供应链/工程/IP/合规事实、使用伪精确评分、因待验证项自动拒绝打样、在不满足条件时生成 4-1 交接包、直接批准量产、修改前序报告/人工资料/原始数据/历史报告或自行维护 `index.html`。

详细检查字段见 [references/review-framework.md](references/review-framework.md)；4-1 交接字段见 [references/handoff-schema.md](references/handoff-schema.md)；正式报告结构见 [templates/report-outline.md](templates/report-outline.md)。
