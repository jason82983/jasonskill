# Precision Brain V3 contract

602 is a complete judgment skill. Its formal execution is `PREPARE → AGENT JUDGE → APPLY`: `prepare_602(product_root, product_code)` reads the current product text and newest timestamped 6-0-1 observation CSV, the current Codex/Agent performs Product Understanding and Precision Judgment, and `apply_602_judgments` validates and projects the structured result. Callers do not provide precomputed decisions or a provider client. If the current Agent cannot judge, fail closed with `AGENT_JUDGMENT_UNAVAILABLE`; the legacy client is test/compatibility-only.

`prepare_602` creates one stable `JudgmentItemId` per canonical keyword and returns facts only. The current Agent then performs Product Profile, Phase A and Phase B/Challenge; `apply_602_judgments` is the deterministic handoff. Phase A receives only product and keyword semantics and returns the structured semantic judgment. Phase B is a late evidence reveal: it receives benchmark coverage/rank and returns only `BenchmarkRealityAssessment` (`SUPPORTS`, `WEAKLY_SUPPORTS`, `NEUTRAL`, `CONTRADICTS`, `INSUFFICIENT`). Phase B cannot replace the Phase A semantic level.

The only `FinalPrecision` values are `高度精准`, `精准`, `弱精准`, and `不精准`. `JudgmentStatus` is separate (`SUCCESS`, `REVIEW_REQUIRED`, `FAILED`). Legacy `PRECISION`, `NOT_PRECISION`, and `REVIEW_REQUIRED` strings are never accepted as `FinalPrecision` values. A failed model item is retained by its stable ID for review; it is never silently matched by array position or replaced by a numeric score.

The model-produced Structured Product Profile must validate core Product Type, Primary Purchase Driver and Core Purchase Mission before keyword judgment. An insufficient profile fails with `PRODUCT_PROFILE_INSUFFICIENT`. Batch size is estimated from the validated profile and prompt size, capped conservatively, and reduced after schema/coverage validation failure. A/B/C/D/E files are deterministic projections of the validated judgment map; no second AI call is allowed during filtering, deduplication, or benchmark splitting. A `REVIEW_REQUIRED` or `FAILED` item retains blank/NULL `FinalPrecision` and is excluded from B/C/D/E; it is never converted to `弱精准`.

For production queues, one user invocation is a `COMPLETE_602_TASK` over dynamic keyword count `N`. The current Agent owns the internal Agent Pull loop: GET batch → Semantic Stage → Benchmark Reality → Decision Challenge → deterministic save → GET next, and Python never calls back into the Agent. Calibrate candidate sizes only as an adaptive runtime probe and select the largest stable size for the unchanged Brain/Profile/runtime; never make a probe value a permanent production limit. Persist completed structured records after every batch and resume from the checkpoint by stable `JudgmentItemId` only after a real platform interruption. `PENDING_JUDGMENT` is an unexecuted item and must not be counted as `REVIEW_REQUIRED`; APPLY is allowed only after PENDING is zero and validation/Golden gates pass. A fixed batch count or normal `RESUME_REQUIRED` exit is prohibited.

The production Agent must drain the queue continuously at the verified maximum safe batch size: GET → JUDGE → SAVE → GET until PENDING is zero or a real execution hard limit occurs. A fixed three-batch stop is not a production rule; progress reporting does not end the loop. Batch size is an execution-efficiency parameter and must not alter the precision kernel.
